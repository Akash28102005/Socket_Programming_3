# UART / SPI / I2C Protocol Simulation and Testing Assignment

Pure-Python simulation of three serial communication protocols — **UART**,
**SPI**, and **I2C** — covering all 21 questions in the assignment brief.
No external hardware or libraries are required; only `pytest` is used for
the verification frameworks (Q7, Q14, Q21).

## Folder structure

```
UART_SPI_I2C_Assignment/
├── requirements.txt
├── README.md
├── logs/                        <- CSV/JSON logs generated by the analyzers
├── uart/
│   ├── transmitter.py           Q1  - UART frame generation
│   ├── receiver.py              Q2  - UART receiver (parity/frame checks)
│   ├── channel.py                Q3  - Tx -> Channel (delay+noise) -> Rx model
│   ├── error_injection.py        Q4  - Deliberate start/data/parity/stop/timeout errors
│   ├── packet.py                  Q5  - Header/Length/Payload/Checksum/EndMarker packets
│   ├── logger.py                  Q6  - Protocol analyzer -> CSV/JSON log
│   └── test_uart.py               Q7  - pytest verification suite
├── spi/
│   ├── master_slave.py           Q8  - Full-duplex Master/Slave transfer
│   ├── modes.py                   Q9  - CPOL/CPHA, Modes 0-3
│   ├── eeprom.py                   Q10 - 256-byte SPI EEPROM (Read/Write/Erase/RDSR/Reset)
│   ├── multi_slave.py              Q11 - Multi-slave bus with Chip-Select routing
│   ├── crc.py                       Q12 - CRC-8 packet integrity check
│   ├── analyzer.py                  Q13 - SPI logic analyzer -> CSV
│   └── test_spi.py                  Q14 - pytest verification suite
└── i2c/
    ├── master_slave.py           Q15 - Start/Address/RW/ACK-NACK/Data/Stop
    ├── register_device.py         Q16 - Register-mapped I2C slave device
    ├── multi_device.py             Q17 - EEPROM + Temp + RTC + Display on one bus
    ├── arbitration.py                Q18 - Multi-master arbitration + clock stretching
    ├── eeprom.py                      Q19 - I2C EEPROM (sequential/random/page/erase/dump)
    ├── analyzer.py                     Q20 - I2C protocol analyzer -> CSV/JSON
    └── test_i2c.py                     Q21 - pytest verification suite
```

## Running the demos

Each numbered file is runnable standalone and prints a demonstration to
the console:

```bash
cd uart && python3 transmitter.py
cd ../spi && python3 modes.py
cd ../i2c && python3 multi_device.py
```

## Running the verification frameworks (Q7, Q14, Q21)

Install pytest once:

```bash
pip install -r requirements.txt
```

Then, from inside each protocol folder:

```bash
cd uart && pytest -v test_uart.py
cd ../spi && pytest -v test_spi.py
cd ../i2c && pytest -v test_i2c.py
```

Each suite prints a pass/fail count per test; pytest's own summary line
at the end (e.g. `18 passed in 0.05s`) serves as the required test report.
To generate a saved report file instead of just console output:

```bash
pytest test_uart.py --tb=short -q > uart_test_report.txt
```

## Logs

Running `logger.py` (UART), `analyzer.py` (SPI), or `analyzer.py` (I2C)
writes CSV/JSON capture files into `../logs/`.

## Notes on design choices

- Every protocol is modeled at the **logical bit/byte level** (Python
  lists of 0/1 or `bytes` objects) rather than with real electrical
  signals, since this is a software simulation assignment.
- Random bit errors, delays, and clock stretching are simulated with
  Python's `random` and `time` modules and are seeded in the tests for
  reproducibility.
- Each question's file can be read and run independently, but later
  questions within a protocol import earlier ones (e.g. SPI's
  `test_spi.py` imports `master_slave.py`, `modes.py`, etc.), matching
  how the assignment builds up complexity question by question.
